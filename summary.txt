FOLDER: test cluade API
========================

WHAT IT IS:
The QA pipeline turned into a service. Same 4-stage check (screenshot →
Gemini → form submit → Airtable verification), but exposed as an HTTP API
so it can be triggered by an Airtable button click instead of by a human
running a script. When the run finishes, the PASS/PARTIAL/FAIL result is
written back to the originating Airtable record automatically.

INTERFACE TYPE:
API based (HTTP webhook server, Flask). Still keeps a CLI fallback.

HOW IT TAKES INPUT:
- Primary: HTTP POST to /run-qa with a JSON body:
      { "record_id": "recXXXXXXXXXXXXXX", "domain": "example.de" }
  Sent by an Airtable Automation when a sales user clicks a button on a
  record in the "EMD Webseiten" table.
- Secondary: still supports the CLI/CSV mode (data.csv with a "domain"
  column) like the other folders.
- Programmatic: a public function `run_domain(domain, airtable_record_id)`
  that any external script can import and call.

HOW IT GIVES OUTPUT:
- HTTP JSON response from the webhook:
      { "status": "PASS"|"PARTIAL"|"FAIL", "message": "...", "details": {...} }
- Write-back to Airtable: PATCHes the "Kontakt status" field on the
  triggering record. Status is set to "testing" while the run is in flight
  (so duplicate clicks don't re-trigger), then to "passed" / "failed" when
  done.
- ui_report.csv + screenshots/ are still produced on disk for batch runs.

HOW TO RUN:
    # Webhook mode
    cd webhook-server
    pip install -r requirements.txt
    python app.py            # listens on 0.0.0.0:5000
    # then point an Airtable Automation webhook at /run-qa

    # CLI mode (same as base "test")
    python visual_qa.py

KEY FILES:
- visual_qa.py            — adds run_domain(), write_qa_result_to_airtable(),
                            set_status_to_testing(), and a SECOND Airtable
                            config (AIRTABLE_TRIGGER_CONFIG) for write-back
- webhook-server/app.py   — Flask server exposing POST /run-qa, GET /health
- webhook-server/Dockerfile + requirements.txt — for deploying the server
- AI_CONTEXT.md           — design doc explaining the two-table Airtable
                            setup (Leads Partner = test target,
                            EMD Webseiten = trigger + result)
- task.txt                — checklist of what's done vs. still to wire up
- form_automation.py / gemini_analyzer.py / airtable_verifier.py — same
  pipeline modules as other folders

HOW IT DIFFERS FROM EVERYTHING ELSE:
- Only folder with a webhook server (Flask).
- Only folder that talks to TWO Airtable tables (one for test-lead checks,
  one for trigger + result write-back).
- Designed to be triggered remotely from Airtable, not by a human.
- No GUI — the "interface" is the Airtable button itself.
